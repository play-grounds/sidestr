an escrow contract, explained

A hash-and-deadline lock on sidestr:txbt4-evm, a sidestr chain that runs Ethereum contracts with sats as gas. The payer locks sats naming a payee, a hash and a deadline: before the deadline only the preimage releases them, and only to the payee; after it only the payer can take them back. No arbiter, no owner, no admin key — the third role is none. Thirty-four lines of Solidity, what each does, and the lock live as this page has validated it. directory

struct Lock { address payer; uint64 deadline; address payee; uint256 amount; bytes32 hash; }
What a lock is: who paid, who can receive, how much, until when, and the hash of the secret that releases it. The field order is deliberate — see the next line.

    
mapping(bytes32 => Lock) public locks; // payer and deadline share one slot
Storage on the chain, keyed by the lock's id. payer (20 bytes) and deadline (8) are written next to each other so they share one 32-byte slot: a lock writes four slots instead of five, saving 20,000 gas — 20,000 sats — by ordering two fields well.

    
event Locked(bytes32 indexed id, address indexed payer, address indexed payee, uint256 amount, uint64 deadline, bytes32 hash);
The log a lock writes. Everything a page needs to show a lock is in this one event, which is how the history below is built.

    
return keccak256(abi.encode(payer, payee, h, deadline));
The id is content-addressed, not a counter: keccak of exactly what the lock says. The payer can compute the id before sending anything, so it goes straight into a link — and nobody can squat on it, because payer is msg.sender and cannot be forged.

    
require(msg.value > 0, "empty"); require(payee != address(0), "nobody"); require(deadline > block.timestamp, "past");
The three ways to make a meaningless lock, refused before anything is written.

    
require(locks[id].payer == address(0), "taken");
The same id means the same lock, so it cannot be overwritten with different terms.

    
function claim(bytes32 id, bytes32 preimage) external {
claim checks no caller. The secret is the authorisation, not the sender: anyone may push a claim through for a payee with no gwei, and the money goes to the payee the lock names whoever pays the gas. One require fewer.

    
require(block.timestamp < l.deadline, "late");
The claim window. < here against >= in refund means the two windows can never both be open — which is what makes the missing caller check safe rather than sloppy.

    
require(sha256(abi.encodePacked(preimage)) == l.hash, "hash");
sha256, not keccak256 — about 60 gas against 36, and in exchange the same secret unlocks a Bitcoin-style HTLC on the sats side of a sidestr chain. The hash is the bridge to everything else; two locks with the same hash on two chains are an atomic swap, and the revealed preimage is the receipt that makes them atomic.

    
delete locks[id]; // delete before paying
The lock is gone before a single wei moves. transfer's 2,300-gas stipend breaks contract payees, so this pays with .call; .call is only safe because the callee runs after the delete — the faucet's "write before paying" lesson, one notch harder.

    
(bool paid, ) = l.payee.call{value: l.amount}(""); require(paid, "payee");
Pay the payee. If the payee is a contract that refuses the money, the claim reverts and the lock stays claimable.

    
require(block.timestamp >= l.deadline, "early");
The refund window: only after the deadline, and only the payer takes it back — that is enforced by the lock's fields, not by checking msg.sender.

how it got here
Compiled with solc 0.8.28, optimiser 200 runs, Cancun rules, from Escrow.sol (the file, and escrow.mjs, the logic this page renders). Deployed to … in block 520 at a cost of 580,854 gas; creation code 2,468 bytes, runtime 2,440. On a throwaway chain the same build charged 114,767 gas for a lock, 41,622 for a claim, 40,482 for a refund, at 1 gwei = 1 sat each. The one assumption the design makes of the chain's VM — a working sha256 precompile at address 0x02 — is checked on this page before anything is built on it. Every number above is read from the page's own copy of the chain, validated here; there is no server behind it.
